# 股票App后端搭建——从数据源踩坑到API跑通

昨晚刚搭完前端架构（React + Tailwind + lightweight-charts），今天一早打开 VSCode，盯着空白的 `server/` 文件夹，心里想的是：后端这摊子怎么铺。

说实话，后端本身不难——Node.js + Express + PostgreSQL 三件套，闭着眼都能写。真正让我头疼的是**数据源**。股票 App 没有实时数据就是个空壳，但免费、稳定、覆盖 A/美/港股的数据源，比想象中难找得多。

## 第一关：数据源选型

我一开始盯上了东方财富的推送接口 `push2.eastmoney.com`。毕竟东财是国内最大的股票数据平台，如果能白嫖它的数据，岂不是美滋滋？

试了一下，直接被现实打脸。

<!-- TODO: 截图：东方财富接口返回的 403 或空数据 -->

东方财富的接口有严格的反爬机制——User-Agent 校验、Referer 检查、频率限制，甚至会检测请求头的完整性。我换了三种伪装方式，每次都能被识别出来。关键是：**即使偶尔成功了，数据延迟也在 3-5 秒**，对于短线分析 App 来说，这延迟等于没有。

然后我开始大海捞针式地试其他方案：

| 数据源 | 免费额度 | A股 | 美股 | 港股 | 延迟 | 稳定性 |
|--------|---------|-----|------|------|------|--------|
| 东方财富 push2 | 无限制 | 有 | 有 | 有 | 3-5s | 差（反爬） |
| Tushare | 200次/分钟 | 有 | 有限 | 有限 | 1-2s | 一般 |
| AKShare | 无限制 | 有 | 有 | 有 | 2-3s | 一般 |
| iTick | 免费层足够 | 有 | 有 | 有 | <50ms | 好 |

最后选了 **iTick**。原因很简单：WebSocket 实时推送，延迟低于 50 毫秒，覆盖 A/美/港股三市，免费层的额度对于 MVP 阶段绰绰有余。而且它有 15 年的 K 线历史数据，回测功能直接就有了。

选型那一刻的感觉——就像在一堆歪瓜裂枣里突然挑到了一个又大又甜的西瓜。**选对数据源，后面的工作量直接砍半。**

## 第二关：把 API 搭起来

数据源定了，接下来就是搭建后端骨架。

整体架构很直接：

```
客户端 (React)
    ↓ HTTP/WebSocket
Express API Server
    ↓
PostgreSQL (用户、持仓、交易记录)
    ↓
iTick API (实时行情 + 历史K线)
```

Express 这部分说实话没什么好说的，标准 CRUD。但有几个设计决策值得记录：

**1. WebSocket 长连接 vs HTTP 轮询**

一开始图省事用 HTTP 轮询，每秒请求一次行情。后来发现一个问题——如果 5 个用户同时在线，每秒就是 5 次请求。用户一多，iTick 的免费额度分分钟烧完。

果断改成 WebSocket 长连接。服务端维护一个连接池，多个客户端共享同一个 iTick 连接。用户看到的价格是同一份数据，但带宽成本降了一个数量级。

<!-- TODO: 截图：WebSocket 连接池的工作流程图 -->

**2. 数据库设计**

PostgreSQL 的表结构围绕三个核心实体：

- `users` — 用户信息 + API 配置
- `watchlists` — 自选股列表
- `trades` — 模拟交易记录（买入/卖出/持仓）

模拟交易的初始资金设为 ¥100,000，A 股遵循 T+1 规则。这个 T+1 的逻辑写在数据库层面，用触发器检查持仓时间，比在应用层判断靠谱得多。

## 踩过的坑

**坑1：iTick 的免费层有连接数限制。** 一开始我为每个客户端都建了一个独立的 WebSocket 连接到 iTick，结果第 4 个连接就被拒绝了。免费层最多 3 个并发连接。解决方案：改成服务端代理模式，所有客户端共享连接。

**坑2：PostgreSQL 的时区问题。** iTick 返回的时间戳是 UTC，但前端要显示北京时间。我一开始在 SQL 里做转换，结果夏令时切换的时候数据错位。后来改成在 Node.js 层统一用 `dayjs` 处理时区，数据库里只存 UTC 时间戳。

**坑3：Express 的 JSON body 大小限制。** 批量导入自选股时，一次性传了 500 多个股票代码，Express 默认的 `body-parser` 限制是 100KB，直接报 413 错误。加了一行 `app.use(express.json({ limit: '10mb' }))` 才解决。

## 学到什么

**数据源选型要先看免费额度和延迟，再看功能。** 东方财富功能最全，但反爬让你根本用不了。iTick 功能不是最全的，但免费 + 低延迟 + 稳定，对于 MVP 来说就是最优解。

**WebSocket 共享连接是必选项。** 任何需要实时数据的 App，如果每个客户端都独立连接数据源，成本和稳定性都会爆炸。服务端代理 + 连接池是标准做法。

**时区问题越早统一越好。** 数据库里永远存 UTC，显示层再转换。这个原则适用于所有涉及时间的系统。

## 以后怎么避免

| 规则 | 频率 |
|------|------|
| 选数据源前先测免费额度上限 | 每次选型 |
| 数据库时间戳统一存 UTC | 永远 |
| WebSocket 连接必须走服务端代理 | 永远 |
| Express body 大小根据业务预估提前设置 | 每次新建项目 |
| 模拟交易规则（T+1 等）在数据库层强制执行 | 永远 |
