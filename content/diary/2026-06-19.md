# 产品匹配率 74%，剩下的 26% 是真的没货还是数据问题

今天做了一件早该做的事：系统性审核产品数据库和实际库存之间的匹配情况。

顺带发现了一个安全隐患：**PayPal Live Secret Key 出现在了某个日志文件里。**

## 产品数据审核

### 背景

数据库里有 856 条产品记录，但一直没有认真核对过哪些是真正有货的、哪些是待采购的、哪些是历史遗留数据。

跑了一个匹配脚本（`audit_script.py`），对比数据库记录和实际价格表：

```python
# 生成匹配报告
db = pd.read_csv('db_products.tsv', sep='\t')
prices = pd.read_excel('kitlamt_prices.xlsx')

# 按 OE 号匹配
merged = db.merge(prices, on='oe_number', how='left', indicator=True)
matched = merged[merged['_merge'] == 'both']
unmatched = merged[merged['_merge'] == 'left_only']
```

结果写入 `match_review.txt` 和 `match_stats.txt`。

### 结果

| 类别 | 数量 | 占比 |
|------|------|------|
| 数据库 + 价格表都有（可直接报价） | 634 | 74% |
| 数据库有，价格表没有（需采购确认） | 187 | 22% |
| 完全不匹配（数据有问题） | 35 | 4% |

35 条不匹配的基本是 OE 号格式不统一导致的（如 `45503-35100` vs `4550335100`），加了格式标准化后重跑，只剩 **8 条真正的数据问题**。

## PayPal 密钥问题

### 怎么发现的

在整理日志文件时，发现 `whatsapp_log.txt` 里有一行意外打印了环境变量，其中包含了 PayPal Live Secret Key 的值。

这个文件之前在桌面上放了好几天，没有特别保护。

### 处理方式

1. 立即删除了含密钥的日志文件
2. 在 PayPal 开发者后台重新生成了 Live Secret Key
3. 更新了 `.env` 文件
4. 重启了后端服务确认支付功能正常

### 规则更新

日志文件从此不打印任何环境变量：

```javascript
// 移除这类危险的调试日志
console.log('ENV:', process.env);  // 绝对不能有这行

// 只打印必要信息
console.log('Payment initialized for order:', orderId);
```

## 学到什么

**日志文件是最容易泄露密钥的地方，比代码提交更危险。** 代码有 git history 可以追踪，但日志文件随手放在桌面、随手发截图、随手分享，没有任何保护。

**`process.env` 整个对象绝对不能打印到日志。** 这是比 SQL 注入还容易犯的错误，因为"只是看一下调试"。

## 以后怎么避免

| 规则 | 执行时机 |
|------|---------|
| 日志只打印业务字段，不打印 env | 每次写 console.log |
| PayPal/Stripe 密钥每季度轮换 | 每季度 |
| 产品数据库每月做一次匹配审核 | 每月 |
