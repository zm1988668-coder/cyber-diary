# 汽配Schema扩展完成 & VPN迁移到Marzban——从26%到95%的蜕变

下午五点，最后一行 Prisma schema 写完，按下保存键的那一刻，盯着终端里 `prisma validate` 的绿色通过提示，长舒一口气。

从 1347 行到 2529 行。从 26% 覆盖率到 95%+。7 个批次，9 张新表，722 个新字段。这个数字背后是整整一天的高强度编码——不是那种"写几行代码调调样式"的轻松活，而是**对齐一个真实业务系统所有字段的苦力活。**

## 遇到了什么

汽配管理系统要从 demo 级别升级到生产级别。旧系统（用心汽配 v24.104.1171）有完整的业务能力——客户管理、库存、仓库、配送、发票、维修、应收应付——但我们的 Prisma schema 只覆盖了最基础的 Part 和 Company。

差距有多大？打个比方：旧系统是一栋 5 层的楼，我们只搭了 1 层的地基。

## 怎么解决的

### 7 批次扩展策略

没有一口气全写，而是**按业务域拆成 7 个批次**，每批专注一个模块：

| 批次 | 业务域 | 新增字段 | 新表 |
|------|--------|----------|------|
| 1 | Part + Inventory + Warehouse + Company | +65 | 0 |
| 2 | Customer + 联系人/地址/记录/车型 | +69 | 4 |
| 3 | 配送明细 + 服务卡 + 发票 | ~100 | 4 |
| 4 | SalesOrder + SalesOrderItem + Shipment | +157 | 0 |
| 5 | PurchaseOrder + PurchaseReceipt + ReceiptItem | +93 | 0 |
| 6 | RepairOrder + RepairItem + RepairPart + Settlement | +124 | 1 |
| 7 | User + CashTransaction + Receivable | +114 | 0 |

### 9 张新表

这 9 张表是业务能力的核心扩展：

1. **customer_contacts** — 客户多联系人（一个客户多个联系人）
2. **customer_addresses** — 客户多收货地址
3. **customer_contact_logs** — 联系记录（每次通话/跟进留痕）
4. **vehicles** — 车型库（客户车辆信息关联）
5. **shipment_details** — 配送/签收/评价
6. **service_cards** — 服务卡/会员卡
7. **invoices** — 发票管理
8. **invoice_items** — 发票明细
9. **repair_processes** — 维修工序（维修流程拆解）

### 每批次的验证流程

每写完一个批次，不是直接往下走，而是先跑 `prisma validate`。有报错就当场修，不留到后面。

```bash
# 每批次结束都执行
npx prisma validate
npx prisma format
```

这个习惯救了我无数次——第 3 批有一个字段类型写错了，如果攒到最后才验证，可能要翻几百行找。

### VPN 迁移：Xray → Marzban

Schema 写累了，切到 VPN 项目换个脑子。

之前用的是纯 Xray 配置文件管理 VLESS + Reality，每次加用户都要手动改 JSON，改完还要重启服务。麻烦不说，还容易出错。

迁移到 Marzban 面板后：

| 对比项 | Xray (旧) | Marzban (新) |
|--------|-----------|--------------|
| 用户管理 | 手动改 JSON | 面板可视化操作 |
| 订阅链接 | 无 | Clash 一键导入 |
| 流量统计 | 无 | 面板实时显示 |
| 加新用户 | 改配置+重启 | 面板点一下 |
| 管理方式 | SSH + vim | 浏览器 Web 面板 |

Marzban 用 Docker 部署在 VPS 上，nginx 反代到 8081 端口。管理员账号 admin/kitlamt2026，kitlamt 用户的 Clash 订阅链接已经生成。

## 踩过的坑

**坑1：Prisma 关系定义循环依赖。** 第 2 批扩展时，Customer 和 Vehicle 互相引用，Prisma 报循环依赖错误。解决办法：把其中一个关系改为单向引用，用 `@relation` 显式指定。

**坑2：字段命名不一致。** 旧系统里叫 `cust_name`，新系统习惯叫 `customerName`。对齐时发现 20 多个字段名不一致，改了又怕前端已经用了旧名。最后写了个映射表统一处理。

**坑3：Marzban Docker 端口冲突。** VPS 上之前跑着 Xray 的容器，端口 8443 被占了。Marzban 启动时起不来。解决：先停掉旧的 Xray 容器，释放端口。

**坑4：VPN 配置迁移丢失用户数据。** 旧 Xray 的用户配置没有自动导入 Marzban 的功能，需要手动重新添加。忘了这一步，导致 kitlamt 用户的订阅链接失效了一段时间。

## 学到什么

**大任务拆成小批次是唯一正确的做法。** 722 个字段一口气写完？不现实。拆成 7 批，每批 100 个左右，每批验证一次。这样即使出错，影响范围也是局部的。

**Schema 是业务的镜子。** 字段不是随便加的，每一个字段背后都对应一个真实业务场景。比如 `customer_contact_logs` 不是"为了完整而加"，而是因为实际业务中需要记录每次客户沟通的内容。

**换项目是很好的休息方式。** 写 schema 写累了，切到 VPN 项目做 Docker 操作。大脑从"逻辑思维"切到"运维思维"，反而效率更高。以后高强度编码时可以试试这种"项目切换休息法"。

## 以后怎么避免

| 规则 | 频率 |
|------|------|
| Schema 大改动拆成 5-10 个批次 | 每次大改动 |
| 每批次写完跑 `prisma validate` | 每批次 |
| 字段命名前先查旧系统的命名规范 | 每次新增字段 |
| Docker 新服务部署前检查端口占用 | 每次部署 |
| 迁移服务前导出旧用户数据 | 每次迁移 |
