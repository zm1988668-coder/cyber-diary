# 两条线并行——汽配Electron化与赛博日记搭建

手指在键盘上停了三秒钟。左边是汽配系统的 Electron 进程，右边是 Quartz 的构建日志。两条完全不同的线，要在今天同时推进。说实话，这种并行任务让我有点兴奋——也有一点焦虑。

但当你把两件事都做完回头看，那种成就感是单线程工作给不了的。

## 汽配系统：从浏览器到桌面

之前汽配系统一直在浏览器里跑，每次都要打开 Chrome、输入地址、等加载。对于一个每天要用 8 小时的工具，这种操作太"远"了。

于是决定把它 Electron 化——变成一个桌面应用。

### 新增文件

```
electron/
  main.ts        — Electron 主进程
  preload.ts     — 预加载脚本（安全桥接）
electron-builder.yml  — 打包配置
```

### RBAC 权限系统

这是今天最大的工程。汽配系统需要多角色协作：

| 角色 | 权限范围 | 说明 |
|------|----------|------|
| Users | 用户管理 | 增删改查用户 |
| Roles | 角色管理 | 分配权限组合 |
| Suppliers | 供应商管理 | 维护供应商信息 |
| Warehouses | 仓库管理 | 库存和仓库操作 |
| Dictionaries | 字典管理 | 系统配置项 |

每个角色能看什么、能操作什么，都通过 RBAC 精确控制。这不是简单的"管理员/普通用户"二分法，而是五个维度的权限矩阵。

### 为什么要做 Electron

| 方式 | 优点 | 缺点 |
|------|------|------|
| 浏览器访问 | 零安装，跨平台 | 依赖网络，界面受浏览器限制 |
| Electron 桌面 | 离线可用，原生体验，可调用系统API | 包体大，更新需要重新打包 |

对于汽配这种高频使用的工具，**离线可用**和**原生体验**比包体大小重要得多。用户不在乎应用占 200MB 还是 500MB，在乎的是点开就能用。

## 赛博日记：从零搭建

另一条线是赛博日记项目。之前一直想做一个个人知识库，但总是在"用什么工具"上纠结。今天终于落地了——选了 **Quartz 4.5.2**。

### 为什么选 Quartz

试了好几个方案：Obsidian Publish（太贵）、Notion（不够 geek）、Hugo（太静态）。Quartz 的优势是：

- 基于 Markdown，本地编辑
- 支持双链（`[[wikilink]]`）
- GitHub Pages 自动部署
- 中文支持好

### 配置细节

```yaml
# quartz.config.ts 关键配置
locale: "zh-CN"
fonts:
  sans: "Noto Sans SC"
  mono: "JetBrains Mono"
theme:
  color: "dark"
```

选了 **Noto Sans SC** 做中文正文，**JetBrains Mono** 做代码字体。深色主题——因为晚上写日记的时候，白色背景太刺眼了。

### GitHub Actions 自动构建

写了一个 `deploy.yml`，每次 push 到 main 分支就自动构建和部署：

```yaml
# .github/workflows/deploy.yml
- name: Build Quartz
  run: npx quartz build
- name: Deploy to GitHub Pages
  uses: peaceiris/actions-gh-pages@v3
  with:
    github_token: ${{ secrets.GITHUB_TOKEN }}
    publish_dir: ./public
```

以后写完日记，`git push` 就完事了。不用手动构建，不用手动部署。

### 每日自动脚本

还写了一个 PowerShell 脚本 `scripts/new-daily-entry.ps1`，每天自动创建新的日记模板。省得每次手动复制粘贴。

## 两条线的交汇点

汽配系统和赛博日记看起来不相关，但其实有一个共同点——**都在解决"入口"问题**。

汽配系统：从浏览器搬到桌面，入口更近。
赛博日记：从散落的笔记搬到统一的知识库，入口更集中。

核心思路是一样的：**减少摩擦，让高频操作变得更容易。**

## 踩过的坑

**坑1：Electron 的 preload 安全策略。** 最开始直接在 renderer 进程里调 Node.js API，结果被 Electron 的安全策略拦住了。后来查了文档，发现必须通过 preload 脚本做桥接。安全是有代价的，但这个代价值得。

**坑2：Quartz 的中文分词。** 默认的搜索功能对中文支持不好，搜"汽配"能找到"汽车配件"，但搜"配件"找不到"汽配"。后来加了中文分词插件才解决。

**坑3：GitHub Pages 的部署延迟。** push 之后不是立刻生效，有时候要等 5-10 分钟。一开始以为是构建失败了，反复触发，结果越等越久。耐心等一下就好了。

## 学到什么

**Electron 不是银弹。** 它解决了桌面化的问题，但引入了新的复杂度：打包、更新、安全策略。选择技术方案时，要清楚自己在"买"什么、在"卖"什么。

**Quartz 的双链是真的好用。** 一旦习惯了 `[[wikilink]]` 的写法，回不去普通 Markdown 了。知识之间的关联变得可见、可维护。

**并行任务的关键是"切换成本"。** 两条线并行时，最浪费时间的不是任务本身，而是从一条线切换到另一条线时的"热身时间"。解决办法是：做完一个完整的小步骤再切换，而不是做到一半就跳。

## 以后怎么避免

| 规则 | 频率 |
|------|------|
| Electron 新功能先查安全文档 | 每次开发 |
| Quartz 构建失败先看 GitHub Actions 日志 | 每次部署 |
| 并行任务用番茄钟切分 | 每天 |
| 中文搜索测试覆盖同义词 | 每次改搜索 |
| push 后等 5 分钟再检查部署 | 每次部署 |
