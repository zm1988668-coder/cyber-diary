# KITLAMT独立站上线——从零到正式运营的一天

早上打开电脑，心里只有一个念头：今天必须把 KITLAMT 独立站上线。

不是那种"有空就做"的上线，是"今天不做完不睡觉"的上线。域名已经买了，VPS 已经就绪，产品数据已经整理好——万事俱备，只差最后那一哆嗦。

结果这一天，干了三件大事：独立站上线、VPN 部署、工作流确立。每一件都踩了不少坑，但每一件最后都跑通了。晚上 11 点关电脑的时候，有一种"今天真的干了很多事"的充实感。

## 第一件大事：KITLAMT 独立站上线

### 搭建过程

技术栈：PHP + MySQL + Nginx，部署在香港 VPS（`45.77.175.209`）上。为什么选香港？因为目标客户是海外汽配批发商，香港的网络对海外访问友好，不需要备案。

<!-- TODO: 截图：KITLAMT 首页截图 -->

产品数据是重头戏——**1084 个 SKU**，覆盖全球主要汽车品牌的零配件。每个 SKU 包含品牌、车型、零件号、适用车型、价格（部分）。

数据源是前端的 `js/partsDB.js`，这是唯一的真相来源。所有产品展示、搜索、筛选都从这个文件读取。后端的 MySQL 只管订单和用户数据。

**为什么前端数据源而不是数据库？** 因为 1084 个 SKU 的查询量不大，前端一次性加载后用 JS 做筛选搜索，响应速度比每次请求数据库快得多。而且改产品数据只需要改一个 JS 文件，不用动数据库。

### 支付系统

Stripe 信用卡支付——这个是最顺利的部分。密钥在 `.env` 里配置好，API 调通，测试交易成功。Stripe 的文档写得确实好，集成体验丝滑。

PayPal 就比较坑了。LIVE 环境配置好，auth 能通，但商户账户被限制审核（`PAYEE_ACCOUNT_RESTRICTED`）。提交了申诉，等审核中。

**没有标价的商品怎么处理？** 这是一个业务设计问题。不是所有商品都有固定价格——有些定制件、大件需要报价。解决方案：无标价商品走 WhatsApp 询盘，客户点"询价"直接跳转 WhatsApp 对话，人工报价后在后台改价，客户再付款。

### 双语支持

i18n 中英文切换，用 `localStorage` 持久化用户选择。这个功能看起来简单，但做起来有讲究——不是所有文字都需要翻译，产品名称、零件号这些保持原文，只有 UI 文案和描述性文字需要双语。

上线那一刻——浏览器输入 `https://www.kitlamtparts.com`，页面刷出来，产品目录、购物车、双语切换全部正常。**1084 个 SKU 全部加载，无报错。**

这种感觉就像开了几个月的车终于拿到了驾照——之前都是练习，今天才算正式上路。

## 第二件大事：VPN 部署

独立站上线后，紧接着搞 VPN。为什么？因为后续的获客工作需要稳定的网络环境，特别是访问 Google Maps、Facebook 这些平台。

用的是 Xray VLESS + Reality 协议。Reality 是比较新的反审查协议，不需要域名、不需要证书，伪装成正常 HTTPS 流量。

部署过程：

```bash
# 在 VPS 上安装 Xray
bash -c "$(curl -L https://github.com/XTLS/Xray-install/raw/main/install-release.sh)" @ install

# 配置 VLESS + Reality
# 生成密钥对
xray x25519
```

配置文件的核心部分：

```json
{
  "inbounds": [{
    "port": 8443,
    "protocol": "vless",
    "settings": {
      "clients": [{"id": "随机UUID", "flow": "xtls-rprx-vision"}]
    },
    "streamSettings": {
      "security": "reality",
      "realitySettings": {
        "dest": "www.microsoft.com:443",
        "serverNames": ["www.microsoft.com"],
        "privateKey": "你的私钥",
        "shortIds": ["随机ID"]
      }
    }
  }]
}
```

Reality 的妙处在于：它连接的"目标网站"是 `www.microsoft.com`，审查系统看到的流量就像是在访问微软官网。**披着羊皮的狼。**

部署完，本地 Clash 导入订阅链接，测试——连上了。速度还不错，延迟大概 80ms。香港 VPS 到国内，这个延迟可以接受。

## 第三件大事：工作流确立

这一天还发生了一件看似不起眼但影响深远的事——**确立了 Agent 工作流**。

之前写代码比较随意，想到什么写什么，经常跳过设计直接动手。结果就是代码质量参差不齐，返工率高。

今天跟 Claude 深聊了一次，定下了六步流程：

| 步骤 | 角色 | 职责 | 输出 |
|------|------|------|------|
| 1 | PM | 出需求 | 需求文档 |
| 2 | 架构 | 拆方案 | 技术方案 |
| 3 | 实现 | 写代码 | 代码 |
| 4 | 审核 | Review | 审核意见 |
| 5 | 测试 | 测试 | 测试报告 |
| 6 | PM | 验收 | 验收确认 |

**为什么要这么复杂？** 因为之前吃过亏——跳过设计直接写代码，写到一半发现方案不对，推翻重来。一个下午就浪费了。

这个流程看起来多了几步，但实际上**总时间更少**。因为每一步都在为下一步铺路，不会出现"写到一半发现方向错了"的情况。

## 还搞定了这些

除了三件大事，今天还顺手做了几件事：

**Playwright MCP 配置。** 替换了已经归档的 Puppeteer MCP，用 `@playwright/mcp@latest`。重启 Claude Code 后生效。以后浏览器自动化操作就用 Playwright 了。

**浏览器不关闭原则确立。** 以后操作 CDP Chrome 时，绝对不能关闭浏览器。因为各平台（Facebook、LinkedIn、外贸通）的登录态都在浏览器里，关了就得重新登录。这个原则是用一次惨痛教训换来的——之前关了一次浏览器，重新登录 Facebook 花了 20 分钟。

**五大获客渠道文档化。** 社媒获客、谷歌地图、展会背调、行业协会、海关数据——每个渠道的优先级和操作方法都写清楚了。以后获客工作有章可循。

## 踩过的坑

**坑1：Nginx 配置 PHP-FPM 路径。** 香港 VPS 的 Nginx 配置里，PHP-FPM 的 socket 路径是 `/run/php/php8.1-fpm.sock`，但我装的是 PHP 8.2。路径不匹配，所有 PHP 页面都返回 502。改了路径才好。

**坑2：PayPal 商户账户受限。** 这个坑不是技术问题，是政策问题。PayPal 对新商户有审核期，特别是涉及跨境交易的。解决方案：先用 Stripe 顶着，PayPal 审核通过后再上线。

**坑3：partsDB.js 文件太大，加载慢。** 1084 个 SKU 的数据全在一个 JS 文件里，文件大小到了 **2.3MB**。首屏加载要 3-4 秒。后来做了懒加载——首屏只加载分类索引，点击具体品牌时才加载该品牌的数据。加载时间从 4 秒降到 **0.8 秒**。

## 学到什么

**上线比完美更重要。** KITLAMT 站不是 100% 完美——PayPal 还没通、部分商品没标价。但先上线、先跑起来，比一直憋在本地"完善"有价值得多。**用户不会等你完美。**

**工作流不是官僚主义。** 六步流程看起来重，但每一步都在减少返工。特别是"审核"这一步——自己写的东西自己很难发现问题，让另一个 Agent 看一眼，经常能发现低级错误。

**VPN 是基础设施。** 对于需要做海外业务的人来说，稳定的网络不是可选项，是必选项。今天部署好，以后所有获客工作都受益。

## 以后怎么避免

| 规则 | 频率 |
|------|------|
| 新项目第一天就部署上线（MVP 级别） | 永远 |
| 每个任务走六步流程（PM→架构→实现→审核→测试→验收） | 永远 |
| 大文件（>1MB）必须做懒加载 | 永远 |
| 操作 CDP Chrome 绝不关闭浏览器 | 永远 |
| PayPal 等第三方支付提前 2 周申请 | 每次新项目 |
| Nginx 配置前先确认 PHP 版本 | 每次部署 |
