# 2026-05-28

## 工作日报

### OpenClaw 升级到 2026.5.28

OpenClaw session 频繁超时（"session file locked, timeout 60000ms"），排查后执行升级：

**问题诊断：**
- trajectory 文件达到 7MB，Gateway 加载超时
- 默认 acquireTimeoutMs 60s 太短
- MiMo V2.5 Pro 实际只支持 128K context，无法扩展到 256K

**修复措施：**
1. 升级 OpenClaw 2026.5.22 → 2026.5.28
2. acquireTimeoutMs：60s → 180s
3. maxHoldMs：5min → 10min
4. maxActiveTranscriptBytes：5MB（超限自动压缩）
5. maintenance.mode：enforce（7天以上 session 自动删除）
6. compaction 优化：maxHistoryShare 0.7，keepRecentTokens 30000

**AGENTS.md 持久化：**
- 确保获客规则跨 session 不丢失
- SOUL.md 作为主魔法（primary spell）保持一致

### cron 自动获客连续超时修复

cron 任务连续 7 次超时（5/28 - 6/1），今天定位到根因：
- 不是 cron 本身的问题，是 OpenClaw session 加载太慢
- 升级 + 超时调整后解决

## 个人复盘

OpenClaw 的性能问题比想象中复杂。最初以为是 cron 任务本身有问题，结果排查发现是 session 管理层的瓶颈。trajectory 文件不断膨胀是核心原因——每次获客任务都会产生大量浏览器操作记录，累积几天就到了几 MB。

MiMo V2.5 Pro 的 128K 上下文限制也是个坑。之前以为可以扩展到 256K，实际测试发现不行。好在通过 compaction 策略（保留最近 30K tokens + 历史压缩到 70%）可以在 128K 内维持较长的对话历史。

## 技术博客

### OpenClaw Session 超时问题的完整排查过程

**现象**：cron 自动任务连续 7 天超时，每次执行到一半就报 "session file locked"。

**排查路径**：
1. 最初怀疑是 cron 任务本身逻辑有问题 → 排除
2. 怀疑是网络问题（浏览器操作慢）→ 排除
3. 最终定位到 session 文件加载：trajectory 7MB + Gateway 默认超时 60s

**为什么 trajectory 这么大？**
- 每次获客任务包含：浏览器导航、页面解析、数据提取、飞书写入
- 每个步骤都记录完整的 DOM snapshot + network log
- 5 天累积就到了 7MB

**解法**：
- transcript 压缩：超过 5MB 自动压缩
- session 清理：7 天以上自动删除
- compaction：保留最近 30K tokens，其余压缩

**教训**：有状态的系统一定要设上限。不限制 transcript 大小，迟早会撑爆。
